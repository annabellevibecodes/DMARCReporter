Fetching Reports from Mailboxes

The Accounts page manages the mailboxes that DMARC and TLS-RPT reports are fetched from. Each account is one mailbox; you can add as many as you need (e.g. one per domain, or one shared inbox across several receivers). Clicking Fetch in the navigation bar — or configuring FETCH_INTERVAL to run automatically — triggers a background run across every enabled account. Progress and the outcome of the last run are shown per account on the Accounts page.

Supported account types:

TypeAuthentication
Generic IMAPUsername and password over TLS
Gmail / Google Workspace Either an app password (requires 2-step verification), or OAuth2: create a Web-application OAuth client in Google Cloud Console, enter its client ID and secret when adding the account (leave the password blank), then complete the Google consent screen you are redirected to. The refresh token is stored encrypted and access tokens renew automatically.
Office 365 / Exchange Online OAuth2 only — Microsoft has disabled basic authentication for IMAP. Register an app in Entra ID with the IMAP.AccessAsApp application permission (admin consent required), grant its service principal mailbox access via New-ServicePrincipal + Add-MailboxPermission in Exchange Online PowerShell, then enter the tenant ID, client ID, and client secret when adding the account.

Use Test on the Accounts page to verify connectivity and mailbox access without fetching or moving anything. Processed emails are moved to a subfolder (created automatically, named to match the server's folder-naming convention) so re-running a fetch never re-imports the same message.

Reading This Dashboard

Pass vs Fail

A message row is counted as passed when it passes DMARC (i.e. SPF or DKIM passed with correct alignment). It is counted as failed when neither check passed with alignment. A high failure rate from a source you recognise usually means misconfigured SPF/DKIM; from an unknown source it may indicate spoofing.

Pass rate

Shown as a percentage of messages from that source that passed DMARC. A legitimate sending service should be at or near 100%. Values well below 100% warrant investigation.

Envelope From vs Header From

The envelope from (return-path) is used for SPF and for bounce delivery. The header from is the address displayed to recipients. DMARC requires alignment between these two. A mismatch highlighted in the report means the sending service is using a different return-path domain, which is common with third-party senders (ESPs, CRMs). Those senders need to either publish DKIM signed with your domain or be added to your SPF record.

Source IPs

Each row in an aggregate report represents one source IP sending mail that claims to be from your domain. Unexpected IPs you do not recognise could indicate a misconfigured service, a compromised account, or an active spoofing attempt.

Provider labels

Where reverse DNS is cached for a source IP, the Sources pages and dashboard show a friendly provider name (Google, Microsoft 365, SendGrid, Mailchimp, and others) instead of a bare IP address, so at a glance you can tell "a known ESP is failing DKIM" from "an unrecognised IP is sending mail as you." Run the Enrich page to populate this for IPs that have not been looked up yet.

Data Enrichment

Use the Enrich page to resolve reverse DNS, WHOIS organisation, ASN and country data for all source IPs, to check DMARC, BIMI, and MTA-STS records for all known domains, and to expand each domain's SPF record into its authorised networks (cached for 24 hours). Enriched data is cached and used throughout the dashboard; until SPF has been expanded the spoof-volume split shows "not resolved yet".
