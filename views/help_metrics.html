How to read an identifier

Small tags such as C5 or S3 appear next to blocks and tables throughout the interface. Each one names a specific metric with a fixed definition, so the same number always means the same thing on the dashboard, on a domain page, in an export and in the API. The letter is the family:

FamilyCoversMainly shown on
C — ComplianceVolume, pass rates, the authentication matrix, disposition and enforcementDashboard, domain pages
S — SourcesWho is sending as you, and how each sending IP behavesSenders, source detail
A — AuthenticationThe raw DKIM and SPF detail behind the pass/fail verdictDomain detail
P — PolicyYour published DMARC record as reporters actually saw itDomain detail
R — ReportersWho sends you reports, how promptly, and report hygieneReporters
T — TLSSMTP TLS reporting (RFC 8460): session success, the policy applied, and why connections failedTLS reports
X — AlertsThe rules that raise alerts — see Alerts & healthAlerts

Unless stated otherwise, every metric counts messages (the count on a report row), not report rows, and obeys the period and domain filters currently selected.

C1–C8 — Compliance

The headline numbers: how much mail there was, how much authenticated, and what receivers did about the rest.

IDMetricWhat it measuresWhere
C1Volume Total messages in the window, with the number of reports, distinct policy domains and distinct reporting organisations behind them. Dashboard tiles
C2DMARC pass rate Share of messages where the receiver's aligned DKIM result or aligned SPF result was a pass. This is the DMARC verdict, not the raw check. Dashboard tiles, trend chart
C3Aligned DKIM pass rate Share of messages whose evaluated DKIM result was a pass, counted on its own. Dashboard tiles, trend chart
C4Aligned SPF pass rate The same for SPF. C3 and C4 overlap: a message can be counted in both. Dashboard tiles, trend chart
C5Authentication matrix Every message placed in one of four cells: both aligned, DKIM only (usually forwarding, where SPF breaks in transit), SPF only (unsigned or broken signing) and neither (misconfigured or spoofed). The cells are exclusive and sum to C1. Dashboard matrix block; each cell links to Senders
C6Disposition split What receivers actually did: delivered (none), quarantine or reject, as volumes and shares. Dashboard enforcement block
C7Enforcement effectiveness Of the mail that failed DMARC, the share receivers actually quarantined or rejected. Shown as n/a while your policy is p=none, since there is nothing to enforce; in that case the block instead shows how much a move to p=reject would block. Dashboard enforcement block
C8Policy overrides Failing mail delivered more leniently than your policy, grouped by the reason the receiver gave. Rows with no <reason> at all are counted separately as unexplained overrides — the ones worth investigating. Reason types are explained under Email authentication. Dashboard "forgiven failures"

S1–S6 — Sources

A source is one IP address that sent mail claiming to be from one of your domains.

IDMetricWhat it measuresWhere
S1Source inventory One row per IP with its own C5 matrix, raw DKIM/SPF results, disposition split, first and last seen, how many reporters saw it, how many header-from domains it sent as, and any label you saved. Senders, source detail
S2New sources IPs whose earliest report anywhere in your data falls inside the selected period — a first appearance, not merely recent activity. Needs a bounded period: with "All Time" every source would be new. Dashboard attention list; "New in period" on Senders
S3Source pattern A label derived from the source's own matrix: healthy (≥90% both aligned), forwarder (≥60% DKIM only), broken signing (≥60% SPF only), spoof suspect (≥95% neither with at least 5 messages), otherwise mixed. Thresholds are the PATTERN_* settings. A classification you save on a source overrides the computed pattern. Pattern chips on Senders
S4Spoof volume The neither mail from C5, split by whether the sending IP falls inside the networks the domain's SPF record authorises. Mail failing from outside SPF is the stronger spoofing signal; mail failing from inside it usually means broken signing. Requires the SPF expansion from Enrich, and reports "not resolved yet" until then. Dashboard spoof block
S5Top failing sources Sources ranked by failure rate rather than volume, above a minimum message count so a single failing message cannot top the list. Dashboard
S6Source enrichment Reverse DNS, a friendly provider name derived from it, and WHOIS organisation, ASN and country. Populated by Enrich and cached; sources appear without it until then. Enrichment column on Senders

A1–A8 — Authentication

Where the C family reports the DMARC verdict, the A family reports the underlying checks. The distinction matters: a message can pass DKIM outright and still fail DMARC because the signing domain does not align. These appear on a domain's detail page.

IDMetricWhat it measures
A1Selector inventory Every DKIM selector seen signing for the domain, with first and last seen, how many distinct sources used it, its pass rate, and an expected flag you set yourself. That flag drives alerts X4 and X5.
A2Raw DKIM results Distribution of the DKIM result reporters recorded (pass, fail, none, temperror, permerror) before alignment is considered, weighted by message count.
A3Signing alignment How each signature's domain relates to the visible From domain: exact, relaxed (same organisational domain, judged with the Public Suffix List) or third party. Includes a histogram of how many signatures each message carried.
A4Raw SPF results The same distribution for the SPF check.
A5SPF scope Whether SPF was evaluated against the envelope sender (mfrom) or the HELO name. A missing scope is counted as mfrom, which is what the standard assumes.
A6Envelope-from alignment Each envelope-from value with its alignment class against the header from: exact, relaxed, misaligned, or the null sender <> used by bounces.
A7Alignment gap Mail where a raw check passed but the aligned result did not — it authenticated for somebody, just not for you. Almost always a configuration problem with a third-party sender rather than an attack, and it lists the domain pairs involved so you can fix it.
A8DNS error rate Share of raw results that were temperror or permerror, per reporting organisation. A spike usually means your DNS was unreachable or your SPF record exceeded its lookup limit, not that senders changed. Drives alert X9.

P1–P6 — Policy

What reporters saw when they looked up your DMARC record. This is the published policy as observed from the outside, which can differ from what you believe you published.

IDMetricWhat it measures
P1Active policy The full published record — p, sp, np, adkim, aspf, pct, fo, discovery_method and testing — for the tuple covering the most mail, plus what each reporter individually saw.
P2Policy consistency Every distinct record seen in the window with the reporters that saw each. More than one means DNS is inconsistent, a change is still propagating, or something is answering differently. Compared on p, sp, adkim, aspf and pct; other tags are displayed but not compared. Drives alert X8.
P3Policy change log An entry each time the majority record changes, with the pass rate for the 7 days before and after, so you can see what a change actually did. Drives alert X7.
P4Subdomain traffic Mail whose visible From domain is a subdomain of the policy domain. Subdomains are governed by sp rather than p, and are a common blind spot.
P5pct sampling Shown only when pct is below 100: the share of failing mail the policy should have skipped versus the sampled_out share reporters actually recorded.
P6Enforcement readiness Whether it is safe to tighten the policy. Under p=none it is the share of mail that would start being blocked. Under an enforcing policy it is the failing volume coming from sources you labelled known_good — legitimate mail already at risk.

R1–R8 — Reporters and hygiene

Metrics about the reports themselves rather than the mail. They answer "can I trust this picture?" — missing reporters mean blind spots, not improvements.

IDMetricWhat it measures
R1Reporter inventory Each reporting organisation with its report count, message volume and share, contact address, and the schema versions it uses.
R2Reporter gaps Reporters that were active in the last 14 days but have sent nothing for ALERT_REPORTER_GAP_DAYS (3 by default), plus a per-day presence strip. A reporter going quiet looks like improvement in every other metric, which is why it is tracked. Drives alert X6.
R3Report latency How long after a reporting window closes the report actually arrives, as a median and 95th percentile per reporter. Reports whose arrival time is unknown are excluded.
R4Window anomalies Reports whose window is not roughly a day (outside 23 to 25 hours). These skew any per-day rate.
R5Duplicates Reports rejected on import because that organisation and report ID were already stored.
R6Parse errors and schema Attachments that failed to parse, with the distribution of report versions and XML namespaces: the original RFC 7489 form versus the newer DMARCbis dmarc-2.0 namespace.
R7Unmanaged domains Policy domains appearing in reports that are not on your managed-domains list — either a domain you forgot to add, or reports arriving for a domain that is not yours.
R8Recipient domains The receiving domains your mail reached, with the pass rate at each. A rate that is poor at one receiver only points at that relationship rather than at your configuration.

T1–T15 — TLS reporting

The T series covers SMTP TLS reports (RFC 8460), which describe the transport security of connections to your mail servers: whether TLS was negotiated, under which policy, and what went wrong when it failed. They say nothing about authentication — a session can be counted here as a success and still be mail that fails DMARC.

Two counting rules worth knowing

Sessions come from the summary, never from the failure rows. Result types are explicitly non-exclusive: one session that hit several errors is reported once per error. So the failure-detail tables (T4–T7, T10, T11, T14, T15) count failure observations, and their total can exceed the session total in T1. Only the policy summary is a session count.

One report can describe the same sessions twice. A reporter that applied both an MTA-STS policy and a TLSA record for the same domain and MX host sends two policy entries covering one set of sessions. Session metrics collapse entries sharing a domain and MX pattern by taking the larger count, not the sum. The reports are stored exactly as they arrived, so the per-report view still shows what the reporter actually sent.

IDMetricWhat it measures
T1TLS success rate Successful sessions as a share of all attempted sessions, overall, per day and per policy domain, with a delta against the preceding window. The headline number.
T2Volume and reporter share Sessions per day and per reporting organisation. Shows both the session-weighted rate and the median of the per-reporter rates — one hyperscaler sending most of the volume otherwise masks a small receiver that fails every time.
T3Policy-type mix Share of sessions under sts, tlsa or no-policy-found, overall and per reporter. The no-policy-found share is the adoption number for your MTA-STS or DANE rollout. Sessions reported under two policy types count under each, so shares can exceed 100%.
T4Failures by result type Failure volume per result type, grouped as the RFC groups them: negotiation (starttls-not-supported, the certificate errors, validation-failure), DANE (tlsa-invalid, dnssec-invalid, dane-required), MTA-STS (the three sts-* errors), plus anything outside the IANA registry.
T5Failures by receiver By receiving MX host, by receiving IP and by HELO name. The per-IP view is the valuable one: a load-balanced or anycast MX shows one bad node while the rest are healthy, and only the IP split reveals it. A HELO that does not match its MX host is itself a finding.
T6Failures by sender By sending MTA, rolled up to network (IPv4 /24, IPv6 /64) and to provider using the same cached reverse DNS and WHOIS as Senders. Answers "one broken node, or everyone?". These hosts send mail to you and are not the same population as DMARC source IPs, so they carry no behaviour classification.
T7Top failure reasons Frequency of failure-reason-code (typically X509_V_ERR_*), overall and within each result type. Free text in the RFC, but repetitive in practice — this is where the root cause behind validation-failure and certificate-not-trusted lives.
T8Policy divergence More than one distinct policy string reported for the same domain on the same day, which means a stale cache somewhere or a divergent policy being served. Comparison against your currently published policy arrives with the DNS snapshots in a later phase.
T9MTA-STS mode and readiness The distribution of observed mode values, and the direct analogue of DMARC enforcement readiness (P6): what the failures observed while in testing would have cost had the policy been in enforce.
T10MTA-STS endpoint health sts-policy-fetch-error, sts-webpki-invalid and sts-policy-invalid over time. These are about the mta-sts.<domain> HTTPS host and the policy file it serves, not about your MX hosts, which is why they have their own panel.
T11DANE and DNSSEC health tlsa-invalid, dnssec-invalid and dane-required, listed with the organisation that reported each one. Every dane-required is a named partner who has pinned mandatory DANE for your domain.
T12TLS reporter coverage Distinct reporters, newly seen reporters, lapsed reporters, days in the period with no report at all, and arrival latency (mail date minus window end). Absence is the point: an attacker suppressing your _smtp._tls record also suppresses the reports.
T13TLS hygiene Duplicates, report-IDs reused across different windows, parse errors, DKIM-rejected reports by reason, unattributed failures, multi-policy reports, odd or multi-day windows, filename/body disagreements, unregistered result types, malformed IPs, and the transport and compression split.
T14IPv4 vs IPv6 How failures divide between address families, for sending and receiving addresses. Broken-on-one-stack-only is common and invisible in an aggregate figure. Note that RFC 8460 puts addresses on failure rows only — a successful session carries none — so this is a split of failures, not a per-family success rate.
T15TLS incidents Consecutive days sharing the same result type and receiving MX host, with first seen, last seen and duration. Turns a spiky chart into a list an operator can work through.

What is counted

A TLS report that arrived as mail without a valid DKIM signature is excluded from every metric above while TLSRPT_REQUIRE_DKIM is on (the default), because RFC 8460 §3 requires receivers to ignore such reports. It is still stored and still listed, with the reason, and T13 counts how many were held back. Reports uploaded through the web form have no carrying message and are never excluded by that rule.

Windows and comparisons

Every metric is evaluated over the period selected on the page, matched against the report's own window start rather than when the report arrived. Dashboard tiles also show a delta against the immediately preceding window of the same length, so "last 30 days" is compared with the 30 days before it.

The same values are available from the API. Each /api/ endpoint accepts period, domain and ef (outbound sender domain), and returns the comparison window alongside the current one when given compare=1.

Because a reporter's window for one day usually arrives during the next, metrics described as covering "the last 24 hours" use a 48-hour window by default (ALERT_RECENT_HOURS). Expect roughly a day of lag before any change in your mail shows up here.
